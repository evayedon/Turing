Code - OSS source and Microsoft's distribution are separate evidence subjects. Public source supports subsystem design claims. It cannot establish the contents of every shipped extension or remote service. Inspect the installed commit separately when the claim depends on the shipped bytes.

**Additional architecture to explore:** profile-specific settings, virtual files and notebook documents, hierarchical settings and extension activation costs, URI provider latency, and graceful reload after renderer failure. Each should be evaluated by its ownership and failure behavior before exposing contribution APIs.

REA `ev_b7c27539e735d08960d8fc08bfa5294623e5e12081b7dd092f6bafbb6017e6fd` parsed the installed 1.40 MB `out/mainImpl.js`. It reported 4 BrowserWindow candidates, 3 dynamic IPC main-handler candidates, 8 sender-validation observations, 1 utility-process candidate, and 10 protocol-registration observations. Confidence is high that these were emitted for the selected file and medium for their interpretation as architectural boundaries. They are static sites and cannot establish how many instances are alive or which handlers authorize each call. Electron semantics were partial and most JavaScript sources were unexamined. The selected bootstrap files returned no Electron call sites, consistent with their narrower role. Use a clean, synthetic desktop project and a process trace to verify one renderer, extension host and PTY workflow end to end.

## Coupling and production implications

A read-only process-name snapshot of the existing VS Code instance on macOS showed the Code executable, four renderer helpers, eight plugin helpers, seven generic helpers, and one Copilot runtime. Confidence is high for the names and counts at the moment sampled. Process names cannot establish worker roles, IPC authorization or per-window ownership. No Xcode executable from its installed bundle appeared in that snapshot. The probe captured executable names only, with no arguments or window contents.

- **Service graph.** VS Code can share cross-window services while scope-specific instances hold editor and workspace state. Model authority as an explicit parameter even when the service is shared. Test that commands targeting a disposed workbench cannot mutate another one. [Workbench bootstrap](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/browser/workbench.ts)
- **Provider model.** Virtual documents and notebooks expose separate identities for buffers, persisted content and sometimes cells or provider-backed resources. Turing can gain this flexibility through URI identity now and defer public provider APIs. Verify generated diagnostics and diff buffers remain read-only and acquire no disk rights. [Virtual documents](https://code.visualstudio.com/api/extension-guides/virtual-documents), [notebooks](https://code.visualstudio.com/api/extension-guides/notebook)
- **Storage and synchronization.** Settings, saved workbench layout, editor recovery and remote workspace state have different scopes. Keep separate migration and retention policy for each. Verify recovery after interrupted write and establish a safe default when a profile cannot be parsed. [Storage source](https://github.com/microsoft/vscode/tree/main/src/vs/platform/storage)
