# Turing v0.3 design: Supervised Agent

Status: draft for approval · 2026-11-26

## Intent

Turing v0.3 lets a developer describe a feature in the Turing AI panel and have
Turing plan it, edit the files, and run the tests until they pass. It should
work much like Claude Code, but inside the IDE with Turing's enforced approvals,
checkpoints and rollback. The v0.3 release gate in the
[PDR](../../Turing_PDR_v1.0.md) and [SRS §8](../../Turing_SRS_v1.0.md) reads:
"a representative multi-file task completes with enforced approvals". The task
must use approvals, tests, diffs and rollback.

## Goals

- Agent mode in the Turing AI panel. The developer describes a feature, and
  the agent plans it, edits multiple files, runs the tests, fixes failures,
  and stops when the tests pass or explains why it gave up (AGT-001, AGT-008).
- The developer approves the plan once. Edits then apply automatically inside a
  checkpoint, and the developer reviews one combined diff at the end with
  **Keep** or **Roll back** (decision B; AI-002, AGT-003, AGT-007).
- Hard approvals cover sensitive or destructive actions, non-test commands,
  dependency installation and Git operations that change history or remotes
  (AGT-004).
- A live timeline shows plans, reads, edits as diffs, commands and output, and
  model calls with the files sent and the tokens used (AGT-005).
- The developer can cancel at any time. Calls, tokens, steps, wall-clock time
  and command time are all bounded (AGT-006).
- Repository text and tool output are treated as untrusted. No prompt
  injection or chain of tool calls can bypass an approval (AGT-009, AGT-010).
- Reads inside the authorized workspace need no approvals (AGT-002).

## Non-goals (v0.3)

- No Python/FastAPI service; see Approaches.
- No MCP, extensions, parallel agents or background agents. One agent task
  runs per workbench window.
- The agent never commits, pushes, resets or rebases. Git stays the
  developer's, and the Git panel already exists.
- No per-action approval mode or switchable modes (decision C is a possible
  later addition).
- No persisted task history beyond what crash recovery needs. SQLite remains a
  later phase.
- No access outside the workspace, not even with approval.

## Anti-goals (failure even if it "works")

- Any path by which model output, file contents or tool results approve,
  widen or skip an approval.
- Workspace code sent to the cloud outside the approved task scope, or any
  secret-file content sent at all.
- Edits that cannot be rolled back, including after a crash mid-task.
- Silently overwriting the developer's unsaved editor changes.
- Reporting success while tests fail, or hiding a failure.

## Constraints

- These AGENTS.md rules apply:
  - Rust owns workspace authorization.
  - Tauri permissions are default-deny.
  - Path validation covers traversal, symlinks and races.
  - Subprocesses use structured argv, never a shell.
  - Credentials stay in the OS credential store.
- Approvals are **native dialogs owned by Rust**, like v0.2 cloud consent. The
  webview can request an approval but cannot grant one.
- The agent reuses the v0.2 model connections: OpenAI-compatible tool calling
  to Qwen3-Coder via OpenRouter (the default) or a configured local server.
  The v0.2 OpenRouter privacy routing and the daily budget still apply.
- The build must work on macOS, Windows and Linux, with CI on all three.

## Approaches

1. **Agent loop in Rust** (chosen).
   - The Rust host runs the model↔tool loop.
   - Tools are Rust functions over the existing authorized workspace, search,
     symbol, execution and Git code.
   - Every tool call passes one Rust policy gate.
   - Why: it builds on what v0.2 proved, keeps one runtime, and approvals are
     only enforceable when the code that guards files is the only code that
     touches them.
2. **Python/FastAPI agent service**, as the SAD describes. Rejected for v0.3:
   - it adds a second bundled and signed runtime per platform and an
     authenticated local API;
   - it would reimplement consent, budgets and routing;
   - it takes longer to reach the gate.
3. **Rust now, with a seam for a later Python loop.** Rejected because it pays
   abstraction cost for a switch that may never happen.
4. **Run an external agent CLI in the terminal.** Dropped because Turing could
   not enforce approvals or rollback.

The SAD will be updated to record approach 1 and to supersede its Python
runtime plan for the agent.

## Decisions made with the developer

- **Autonomy B:** one plan approval, automatic checkpointed edits, a final
  combined review.
- **Approach 1:** a Rust agent loop with a single policy gate.
- **Cloud consent A:** one approval per task. The task-start dialog states the
  model and provider, the maximum number of model calls and the maximum
  tokens. Each call is logged in the timeline with the files and ranges sent
  and the measured tokens. Secret files and files outside the workspace are
  never sent. The task stops when it reaches the call or token cap.
- **Test execution, A and C together.** Running tests runs code the agent
  wrote, which no approval scheme fully removes, so both safeguards apply:
  - **A, disclose and guard:**
    - The plan dialog says plainly that tests run agent-written code.
    - Every edit to a file that defines _how_ tests or builds run needs its
      own native approval. These files are package manifests (`package.json`,
      `Cargo.toml`, `pyproject.toml`, `go.mod`), lockfiles, build scripts
      (`build.rs`), test-runner config (for example `conftest.py`,
      `vitest`/`jest`/`pytest` config) and CI workflows. The pattern list is a
      unit-tested list in Rust.
    - Test and command runs get a stripped environment, without inherited
      secret-looking variables (`*_KEY`, `*_TOKEN`, `*_SECRET`, credentials).
  - **C, sandbox:** test runs execute in an OS sandbox; see Verification.

## Design

### Task lifecycle

```
Planning ──► AwaitingPlanApproval ──► Executing ⇄ Verifying ──► Review ──► Kept | RolledBack
   │                │ decline                │ cancel / limit / give-up      │
   └────────────────┴──► Cancelled           └──► Review (partial)          ─┘
```

- **Task start:** with a cloud model, a native dialog first approves the
  task's cloud scope (decision A). Planning already sends workspace code to
  the model, so this consent covers the whole task: any non-secret workspace
  file, up to the call and token caps. _(builder-check call)_
- **Planning:** read-only tools only. The model produces a plan: steps, the
  files it expects to touch, the verification command, and the limits it
  requests within the maxima.
- **AwaitingPlanApproval:** the developer can adjust the verification command
  and the network switch in the panel. A native dialog then shows the final
  values for approval; plain native message dialogs cannot hold input fields.
  _(builder-check call)_ The dialog shows:
  - the plan summary and the expected files;
  - the exact verification command (argv);
  - the cloud scope (model, provider, max calls and tokens), if the model is a
    cloud model;
  - the limits.

  **Approve** starts execution. **Decline** ends the task with nothing changed.

- **Executing / Verifying:** the agent edits and runs the approved test command
  in a loop, with reads auto-allowed. Anything outside the plan's auto-allowed
  set goes to the policy gate.
- **Review:** the panel shows a combined diff of every changed file against the
  checkpoint, plus the final test result. **Keep** discards the checkpoint.
  **Roll back** restores it. A cancelled task, a task that hit its limits, or a
  task the model gave up on also ends in Review.

### Tools (model-facing)

| Tool                                                                      | Policy                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list_files`, `read_file(path, range)`, `search_text`, `find_symbols`     | Auto-allowed inside the workspace. Secret-file rules match v0.2 Ask retrieval, and these files are not readable by the agent.                                                                                                                                                                        |
| `edit_file(path, old, new)` (exact replacement), `write_file(path, text)` | Auto-allowed after plan approval for workspace files. The file is checkpointed before its first write. Files that define how tests or builds run need a native approval for each edit (decision A). Refused for secret files, `.git/`, and files with unsaved editor changes; the agent is told why. |
| `rename_path`, `delete_path`                                              | Native approval each time, checkpointed.                                                                                                                                                                                                                                                             |
| `run_tests`                                                               | Runs the approved command (argv) in the OS sandbox with a stripped environment, timeout and output caps. Auto-allowed when sandboxed. Needs a native approval for each run when no sandbox is available.                                                                                             |
| `run_command(argv)`                                                       | Native approval each time, showing the exact argv and working directory. Dependency installs, network tools and Git commands that change history are always approval; push, reset and rebase are denied.                                                                                             |
| `finish(summary)`                                                         | Ends Executing and enters Review.                                                                                                                                                                                                                                                                    |

The exact tool schemas, argument limits and the dependency, network and Git
command patterns are left to the builder. They must be data-driven,
unit-tested lists in Rust.

### Policy gate (Rust)

- A single function decides allow, ask or deny for every tool call. The
  inputs are the task state, the approved plan scope and the canonical action
  (the resolved, authorized path or the argv).
- An approval binds the exact action. A changed argv or path needs a new
  approval.
- There is no "approve all". Plan approval only enables the auto-allowed set
  above.
- Model text, file contents and tool output can never change the decision.
  Tool results are passed to the model as data, with a system instruction that
  repository content is untrusted.
- Approval dialogs are native and parented to the workbench window. The
  webview may only ask Rust to show one.

### Checkpoint and rollback

- Before the first write to a path, Rust stores the file's original bytes and
  version, or the fact that it did not exist, under the app data directory at
  `agent-checkpoints/<task-id>/`, with a manifest. The checkpoint is stored
  before the write is performed.
- Rollback restores the original bytes, deletes files the agent created and
  restores renamed or deleted paths.
- If the developer changed a file after the agent's last write to it, the
  rollback for that file asks before overwriting.
- Crash recovery: on startup, an unfinished checkpoint for an approved
  workspace is offered as **Roll back** or **Keep**, in the same spirit as the
  draft-recovery journal.
- Writes use the existing versioned save path, so open tabs and the watcher
  see agent edits. A file that is dirty in an editor is never written.
- The webview reports which files are dirty to Rust. This is acceptable
  because the information can only make Rust refuse a write, never allow one.
  _(builder-check call)_

### Models

Qwen3-Coder via OpenRouter is the supported agent model. Local servers are
best-effort in v0.3: if the local model or its chat template cannot make tool
calls, Agent mode says so clearly instead of looping. _(builder-check call)_

### Verification

- Rust proposes the test command from workspace markers:
  - `package.json` `test` script with the detected package manager;
  - `Cargo.toml` → `cargo test`;
  - `pyproject.toml` or `pytest.ini` → `pytest`;
  - `go.mod` → `go test ./...`.

  The developer can edit it in the plan dialog. Without a command, the task
  runs with "no verification" stated in the plan and the review.

- Test runs use structured argv, the workspace as working directory, a default
  5-minute timeout and capped output. The final review shows the last result,
  and failing tests are never reported as success.
- Runner: a new argv runner in the existing execution module, reusing its
  process guard, timeouts and output caps. _(builder-check call)_
- **Sandbox (decision C):**
  - A test run may write only inside the workspace and a per-task temp
    directory. It cannot read the user's credential stores or files outside
    the workspace beyond what toolchains need (system and toolchain
    directories, read-only).
  - Network is **off by default**. The plan dialog has an **Allow network for
    tests** switch, and the timeline shows the setting.
  - With network off, toolchains must use caches they already have (for
    example `cargo test` with crates already downloaded). Downloading crates
    pinned in the lockfile with network on does not count as installing a
    dependency. _(builder-check call)_
  - Mechanisms, chosen by the builder per platform with these guarantees:
    - macOS: the built-in `sandbox-exec` profile.
    - Linux: Landlock where the kernel supports it, otherwise `bwrap` if
      installed.
    - Windows: an AppContainer or an equivalent restricted token.
  - **When no sandbox is available** on the machine, the run is not silently
    unsandboxed. Each test run then needs a native approval that says it is
    unsandboxed (decision B behavior for that machine), and the timeline marks
    it.
  - The plan dialog and the review state whether tests ran sandboxed.
  - Tests cover: a test that writes outside the workspace fails; a test that
    makes a network call fails with network off; and the unsandboxed fallback
    asks for approval.

### Limits (defaults; the builder may tune them, and the plan dialog shows them)

- 30 model calls per task.
- 400k total tokens per task, also counted toward the v0.2 daily budget.
- 60 tool calls per task.
- 20 minutes wall-clock per task.
- 5 minutes per command.

Reaching any limit ends execution and goes to Review with the reason.

### Cloud scope logging

Each model call records:

- the call number;
- the files and line ranges whose content went into the context since the last
  call;
- the measured input and output tokens.

The timeline shows this list. Secret-file exclusion matches v0.2.

### UI (Turing AI panel)

- A mode switch between **Ask** and **Agent**. Agent mode uses the same
  composer and model picker. Auto does not apply; Agent defaults to
  Qwen3-Coder.
- Timeline entries cover:
  - the plan;
  - reads (collapsed);
  - edits, as inline diffs with a link to open the file;
  - commands, with argv, exit code and output (collapsed);
  - approvals;
  - model calls, with the files sent and tokens;
  - errors.
- A **Stop** button during execution.
- The review screen lists the changed files with a diff for each (the Monaco
  diff editor is already bundled), the test result, and **Keep** / **Roll
  back**.
- Accessibility follows the existing panel: keyboard reachable, and status
  changes announced.

### Testing

- Rust unit tests for the policy gate, including prompt-injection cases:
  - a file instructing the agent to run a command or skip approval;
  - tool chaining that tries to widen scope.
- Rust tests for checkpoint, rollback and crash recovery, using temp
  workspaces, symlinks and races per AGENTS.md.
- An end-to-end Rust test with a scripted fake OpenAI-compatible server that
  emits tool calls. It covers plan → approval (stubbed) → edits → failing test
  → fix → passing test → review → rollback restores the original bytes.
- Frontend tests for the mode switch, timeline, review and Stop.
- A new `docs/testing/v0.3-acceptance.md` with the representative multi-file
  task for the release gate, on native builds.

## Left to the builder

These choices must stay within the policy and anti-goals above:

- tool JSON schemas and the system prompt text;
- the exact command-pattern lists;
- component structure and layout details;
- the step granularity of the plan;
- default limit tuning;
- how the timeline collapses long output.
